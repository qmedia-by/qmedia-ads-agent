# Доступ к Google Ads MCP ограничивают список Test users и allowlist Аккаунтов

Наш экземпляр `google-ads-mcp` — публичный HTTPS-эндпоинт на хостинге агентства, работающий на developer token агентства. Без ограничений любой, кто узнал URL, расходовал бы нашу квоту и ходил бы в Google Ads через нашу инфраструктуру.

Изначально мы планировали Cloud Run IAM, но, во-первых, от Cloud Run пришлось отказаться целиком ([ADR-0002](./0002-centrally-hosted-google-ads-mcp.md)), а во-вторых, IAM требует от клиента Google identity token в каждом запросе, чего MCP-клиенты не умеют — они знают только про OAuth самого MCP-сервера.

Ни IAM, ни IAP не понадобились. Наше OAuth-приложение остаётся в статусе Testing ([ADR-0007](./0007-oauth-app-stays-in-testing.md)), а Google в этом статусе пускает только аккаунты, вручную внесённые в список **Test users**. Это и есть контроль доступа по пользователям, встроенный в OAuth: чужой аккаунт не получит токен, и до нашего сервера дело не дойдёт.

## Второй слой: какие Аккаунты

Список Test users отвечает на вопрос «кто войдёт», но не на вопрос «куда вошедший дотянется». Для агентства, где Менеджеры имеют доступ ко всему MCC, одного этого слоя мало: агента ничто не удерживало от похода в Аккаунт не того Клиента — например, по опечатке в `customer_id`. [Реестр](./0008-account-registry-single-source.md) направляет агента, но сам по себе не принуждает его.

Второй слой — сам [Реестр](./0008-account-registry-single-source.md): сервер отклоняет вызовы инструментов для Аккаунтов, которых в нём нет, а выдачу `list_accessible_customers` фильтрует.

Слоя долго **не существовало** — ни в upstream, ни в форке. Переменная `GOOGLE_ADS_ALLOWED_CUSTOMER_IDS` попала в наши ранние документы по ошибке, из непроверенного источника, и генератор печатал значение в никуда. Закрыть это можно было только кодом в форке: 13 августа 2026 слой реализован отдельным модулем `ads_mcp/access_control.py`.

Тогда он читал ту самую переменную, а её значение приходилось переносить в `.env` из Реестра руками. Список Аккаунтов существовал в двух местах и предсказуемо расходился — симптомом был отказ по Аккаунту, который в Реестре уже есть. С переездом Реестра в таблицу переменная удалена: allowlist собирается прямо из Реестра. Подробности — в `FORK.md` форка.

## Последствия

Подключение Клиента — одна операция: строка в Реестре. Расходиться больше нечему, потому что второго места, где живёт список Аккаунтов, не существует. Изменения подхватываются в течение пяти минут; поиск Клиента по имени видит их сразу, потому что промах по имени заставляет сервер перечитать таблицу.

Незаданный Реестр означает отсутствие ограничений — это поведение upstream, и оно же позволяет гонять тот же образ локально без service account. Чтобы такой режим нельзя было включить опечаткой, preflight деплоя требует от переменных Реестра **непустого** значения.

Реестр, который сконфигурирован, но не читается, ограничений не снимает, а наоборот: сервер отказывает по всем Аккаунтам. Неизвестный allowlist — не пустой, и молча превратить один в другой было бы худшим из возможных отказов. На практике это редкость: сервер держит последний удачный снимок и переживает на нём и недоступность Google, и собственный перезапуск.

Границы **между Клиентами** этот слой не охраняет: он ограничивает периметр агентства, а внутри периметра Менеджер по-прежнему дотянется до Аккаунта чужого Клиента. Для этого понадобился бы allowlist на каждого Менеджера, а токен у сервера один на всех — такое решение не принято и в MVP не нужно.
