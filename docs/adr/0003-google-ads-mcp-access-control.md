# Доступ к Google Ads MCP ограничивает список Test users

Наш экземпляр `google-ads-mcp` — публичный HTTPS-эндпоинт на хостинге агентства, работающий на developer token агентства. Без ограничений любой, кто узнал URL, расходовал бы нашу квоту и ходил бы в Google Ads через нашу инфраструктуру.

Изначально мы планировали Cloud Run IAM, но, во-первых, от Cloud Run пришлось отказаться целиком ([ADR-0002](./0002-centrally-hosted-google-ads-mcp.md)), а во-вторых, IAM требует от клиента Google identity token в каждом запросе, чего MCP-клиенты не умеют — они знают только про OAuth самого MCP-сервера.

Ни IAM, ни IAP не понадобились. Наше OAuth-приложение остаётся в статусе Testing ([ADR-0007](./0007-oauth-app-stays-in-testing.md)), а Google в этом статусе пускает только аккаунты, вручную внесённые в список **Test users**. Это и есть контроль доступа по пользователям, встроенный в OAuth: чужой аккаунт не получит токен, и до нашего сервера дело не дойдёт.

## Чего у нас нет

Второй слой — ограничение на то, **какие Аккаунты** этот деплой вправе запрашивать — задуман, но **не реализован**. Переменной `GOOGLE_ADS_ALLOWED_CUSTOMER_IDS`, на которую мы рассчитывали, в официальном сервере не существует: она попала в наши документы по ошибке, из непроверенного источника. Код upstream знает только `GOOGLE_ADS_DEVELOPER_TOKEN`, `GOOGLE_ADS_LOGIN_CUSTOMER_ID`, `GOOGLE_ADS_MCP_*`.

Пока слоя нет, границы доступа задают две вещи: список Test users определяет, кто войдёт, а права в самом Google Ads — к каким Аккаунтам вошедший дотянется. Для агентства, где Менеджеры имеют доступ ко всему MCC, это означает, что агента ничто не удержит от похода в Аккаунт не того Клиента — например, по опечатке в `customer_id`. [Реестр](./0008-account-registry-single-source.md) направляет агента, но не принуждает его.

Закрывается это только кодом в форке. Решение не принято.
