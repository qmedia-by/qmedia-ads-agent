# Реестр Аккаунтов — источник связки «Клиент → Аккаунты»

Агент должен уметь ответить на вопрос «какие Аккаунты есть у этого Клиента». Динамическое обнаружение через `list_accessible_customers` эту задачу не решает: инструмент возвращает голые числовые идентификаторы без названий, и Менеджер, ведущий два десятка Клиентов, не опознает среди них нужного.

Кладём в репозиторий Реестр — read-only файл, связывающий Клиента с его Аккаунтами у разных Провайдеров. Формально это противоречит [ADR-0006](./0006-repository-holds-no-state.md), но противоречие мнимое: Реестр не пишется агентом, меняется раз в месяц при подключении Клиента и проходит ревью в PR. Это конфигурация, а не состояние.

Изначально предполагалось, что тот же файл станет источником для серверного allowlist Аккаунтов. Этого механизма не существует — см. [ADR-0003](./0003-google-ads-mcp-access-control.md). Пока он не реализован, Реестр остаётся указателем для агента и ничего не запрещает на стороне сервера.

## Последствия

Реестр направляет, но не принуждает: агент, которому Менеджер продиктовал `customer_id` напрямую, пойдёт по нему, даже если Клиента в Реестре нет. Инструкции требуют начинать с Реестра, но это дисциплина, а не контроль.

Скрипт `scripts/allowed-customer-ids.mjs` печатает список `customer_id` из Реестра. Он написан под несуществующую переменную окружения и до реализации allowlist полезен только для ручной сверки.
