# Реестр Аккаунтов — источник связки «Клиент → Аккаунты»

Агент должен уметь ответить на вопрос «какие Аккаунты есть у этого Клиента». Динамическое обнаружение через `list_accessible_customers` эту задачу не решает: инструмент возвращает голые числовые идентификаторы без названий, и Менеджер, ведущий два десятка Клиентов, не опознает среди них нужного.

Кладём в репозиторий Реестр — read-only файл, связывающий Клиента с его Аккаунтами у разных Провайдеров. Формально это противоречит [ADR-0006](./0006-repository-holds-no-state.md), но противоречие мнимое: Реестр не пишется агентом, меняется раз в месяц при подключении Клиента и проходит ревью в PR. Это конфигурация, а не состояние.

Тот же файл — источник для серверного allowlist Аккаунтов ([ADR-0003](./0003-google-ads-mcp-access-control.md)): `scripts/allowed-customer-ids.mjs` печатает из него значение `GOOGLE_ADS_ALLOWED_CUSTOMER_IDS`. Механизма долго не существовало, и до его появления Реестр не запрещал на стороне сервера ничего.

## Последствия

Реестр направляет, а принуждает лишь на периметре агентства. Аккаунта, которого в Реестре нет, агент не получит: серверный allowlist собран из Реестра, и вызов отобьётся — но только пока `.env` на сервере с Реестром не разошёлся. Внутри периметра Реестр по-прежнему ничего не охраняет: Менеджер, продиктовавший `customer_id` чужого Клиента агентства, пройдёт. Инструкции требуют начинать с Реестра, и вот это остаётся дисциплиной, а не контролем.

Скрипт `scripts/allowed-customer-ids.mjs` (`npm run allowed-ids`) печатает список `customer_id` из Реестра — готовое значение для `GOOGLE_ADS_ALLOWED_CUSTOMER_IDS` на сервере. Подключили Клиента — перегенерируйте и обновите `.env`.
